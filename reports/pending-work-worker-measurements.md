## Method and caveats
- **Machine was not idle.** Load average 6 to 15 during the run, another agent ran test modules in the worktree, and other Claude sessions were active. /api/list is ~1 MB and takes 270-360 ms here, so absolute numbers are inflated and p95 is noisy. Repeated where it looked noisy.

The branch server ran from an rsync copy of the working tree (excluding `.git`) in the scratch dir, so scans wrote the copy's `aitracker/pending.json`, never the worktree's (verified: worktree `pending.json` unchanged, 921,159 B, mtime 17:08). The copy started with the real 921,159 B report.
- Ports 18811 (branch), 18812 (base), 18813 (M7) instead of 8811/8812/8813. Every server had `TRACKER_SCHEDULER_AUTOINSTALL=0 TRACKER_NO_BROWSER=1 TRACKER_PENDING_INTERVAL=off`, `TRACKER_AUTH` unset. Scans ran with `TRACKER_PENDING_CLEAN=dry-run` only, and a `gh` shim that exits 1 (no network). Two real scans in total (M4 full, M9 killed at 15 s).
- Scratch: `/Users/pritammondal/.claude/jobs/8b05c822/tmp/measure/` (scripts and logs).

## FAIL analysis (no code changed)

### M8: item detail 4.3-7.5 s for the largest worktree
- Where: `aitracker/pending.py:1152-1161`, `item_detail`. It runs `rev-parse`, then four git commands serially (`status --short`, `diff HEAD --stat`, `diff HEAD`, `log HEAD --not --remotes`) through `_git_capped`. The slow item is the 234-dirty-file `fe-nx` worktree (a large Nx monorepo); the other four items answer in 0.3-0.6 s, so the cost is git on that tree (`status` was the dominant scan cost too: mean 128 ms per call across the scan, far more on big trees), not Python.
- Likely cause: the four git calls are serial, each re-scans the index and 234 changed files, and `diff HEAD` has no early exit apart from the 256 KB kill. The cap limits bytes, not wall time.
- Fix direction: run the four calls concurrently (a small thread pool, they are independent), and give `item_detail` an overall time budget (for example 2 s) that returns the parts finished so far plus a "(truncated: git slow)" fence. Do not remove the byte cap. Test: a fixture with a patched `_git_capped` that sleeps, asserting the response returns inside the budget with a truncation note.

### M10: test time 277 s against 90 s
- `tests/test_pending_clean.py` takes 176.8 s: `test_off_mode_and_unknown_mode_do_nothing` 31.2 s (three `scan_clean` calls, about 10 s each), `test_git_timeout_keeps` 24.3 s, `test_git_remove_failure_keeps` 13.0 s, `test_unpushed_survives_and_fresh_survives` 12.2 s, `test_toctou_head_moved_survives` 10.5 s. Each `scan_clean` does a full real scan, which here runs real git in a fixture repo under load. `tests/test_update.py` adds 50.9 s (top: `test_preflight_failures_leave_head_alone` 6.2 s, `test_refusals` 5.2 s, `test_fetch_has_no_controlling_terminal_and_dies_on_timeout` 4.6 s).
- `tests/pending_fixture.py:70-71` already copies from a template (`copytree`), so F15's template half exists; the remaining cost is the scan itself and real timeouts in `test_git_timeout_keeps` (it waits out a real git timeout).
- Fix direction: in `test_pending_clean.py`, stub `_nice` to `[]` and shrink the git timeout constant for the timeout test (patch the constant, not the production value); use `mode="off"`/`"bogus"` loops against one scan result rather than three scans (`test_off_mode_and_unknown_mode_do_nothing`); scan only the one fixture repo instead of the discovery path. Do not weaken the assertions. Re-measure on an idle machine before judging: this run overlapped other sessions, and the budget is stated for an idle machine.
- Side check: `pgrep -x sleep` showed 2 sleeps after the run; both belong to other sessions (a `/bin/sleep 9` loop from another job), not to `test_update_restart`.
